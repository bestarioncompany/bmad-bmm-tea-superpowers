I
What is Superpowers?
Superpowers Playbook — disciplined execution layer for implementation
Add-on Module
Phase 4 Execution

Superpowers is an execution add-on for Phase 4. BMAD keeps product context, sprint governance, and the delivery ledger. TEA keeps test architecture and release evidence. SPP owns the coding loop: approved spec, clean workspace, exact plan, small implementation slices, TDD, review, and verification. Branch finish remains a document-guided prompt path, not a Phase 4 card.

SPP does not replace BMAD or TEA. It gives the implementation driver a stricter operating system so each handoff is durable, each claim has evidence, and each worker can continue from files rather than chat memory.

II
8 Core Principles
SPP decisions follow these enterprise execution guardrails
Source
spp_docs.html + spp-*.html
01
Skill routing is mandatory — Route to the relevant Superpowers skill before acting. Do not rationalize with too simple, already know this, or just this once. When BMAD/TEA are present, name the active driver explicitly.
02
Design precedes code — Clarify one question at a time and compare meaningful approaches. Write the approved spec as a durable artifact before planning. No implementation code or scaffolding before approval.
03
Plans are execution contracts — Plans include exact files, interfaces, commands, expected output, and no placeholders. Tasks are small enough to test and review independently. RED-GREEN-REFACTOR is embedded in the plan.
04
TDD is an iron law — No production behavior without a failing test observed first. Code written before the failing test is deleted and restarted. GREEN means minimal implementation; refactor only after green.
05
Debug root cause first — Reproduce, read errors, check recent changes, trace data flow, then hypothesize. Test one hypothesis with the smallest useful change. After repeated failed fixes, question architecture instead of stacking patches.
06
Review early, receive skeptically — Task review checks both spec compliance and code quality. Critical/Important findings block forward progress. External review feedback is verified against the codebase before implementation.
07
Evidence beats claims — No completion claim without fresh command output and exit-code evidence. Previous runs, agent reports, and partial checks are not completion evidence. Final status reconciles tests, requirements, baseline, review closure, and diff.
08
Artifacts survive memory — Specs, plans, task briefs, reports, review packages, ledgers, and verification summaries carry state across sessions. Scratch SPP evidence belongs in self-ignored SPP space such as .superpowers/sdd/ when used. BMAD story/status and TEA evidence remain the governance wrapper around SPP execution.

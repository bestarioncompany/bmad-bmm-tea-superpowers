Mental Model

SPP does not replace all of BMAD. It replaces the coding driver inside Phase 4 with a clear sequence of gates: design first, clean workspace, concrete plan, small tasks, TDD, review, verification, and branch finish.

Rule: BMAD owns planning/status, SPP owns coding execution, TEA owns test architecture and release evidence.

SPP Core Principles

These rules are the common operating spine behind every SPP card. They align the official Superpowers workflow with BMAD story governance and TEA quality evidence.

1. Skill routing is mandatory
  • Route to the relevant Superpowers skill before acting.
  • Do not rationalize with too simple, already know this, or just this once.
  • When BMAD/TEA are present, name the active driver explicitly.
2. Design precedes code
  • Clarify one question at a time and compare meaningful approaches.
  • Write the approved spec as a durable artifact before planning.
  • No implementation code or scaffolding before approval.
3. Plans are execution contracts
  • Plans include exact files, interfaces, commands, expected output, and no placeholders.
  • Tasks are small enough to test and review independently.
  • RED-GREEN-REFACTOR is embedded in the plan, not remembered later.
4. TDD is an iron law
  • No production behavior without a failing test observed first.
  • Code written before the failing test is deleted and restarted.
  • GREEN means minimal implementation; refactor only after green.
5. Debug root cause first
  • Reproduce, read errors, check recent changes, trace data flow, then hypothesize.
  • Test one hypothesis with the smallest useful change.
  • After repeated failed fixes, question architecture instead of stacking patches.
6. Review early, receive skeptically
  • Task review checks both spec compliance and code quality.
  • Critical/Important findings block forward progress.
  • External review feedback is verified against the codebase before implementation.
7. Evidence beats claims
  • No completion claim without fresh command output and exit-code evidence.
  • Previous runs, agent reports, and partial checks are not completion evidence.
  • Final status reconciles tests, requirements, baseline, review closure, and diff.
8. Artifacts survive memory
  • Specs, plans, task briefs, reports, review packages, ledgers, and verification summaries carry state across sessions.
  • Scratch SPP evidence belongs in self-ignored SPP space such as .superpowers/sdd/ when used.
  • BMAD story/status and TEA evidence remain the governance wrapper around SPP execution.

New User Operating Path

If you are new to SPP, read the cards as a chain of gates. Each gate has one job: turn uncertain context into durable evidence the next worker can trust.

1. Shape the story
BMAD Create Story first turns backlog into {story_key}.md. SP-A then turns that ready story into an approved spec before implementation planning.
2. Protect the workspace
SP-B detects isolation and records baseline results so later verification can separate new regressions from old failures.
3. Make execution explicit
SP-C writes exact tasks, files, interfaces, red/green commands, expected output, and no placeholders.
4. Execute in reviewed loops
SP-D dispatches fresh workers, SP-E enforces TDD, SP-F stops guessing, and SP-G reviews before defects compound.
5. Prove completion
SP-H requires fresh evidence for every claim: tests, requirements, baseline comparison, review closure, and final diff inspection.
6. Finish deliberately
SP-I packages the verified branch and asks the user to choose merge, PR, keep, or discard before any outward-facing action.

Detailed Card Notes

04 · SP-A - Brainstorming & Spec

Superpowers brainstorming is the design-discovery entry point after BMAD Create Story. It absorbs the ready story file, asks focused clarification questions, explores alternatives, and writes a spec that becomes the source of truth for the plan.

Why
Starting implementation from raw epic intent creates assumption drift. This card starts from the BMAD story file and forces explicit user approval before the team moves from story intent to plan.
How
Use the brainstorming skill with one question at a time, capture constraints and trade-offs, then save the approved spec under docs/superpowers/specs/.
Operating rules
  • Do not write implementation code, scaffold files, or invoke implementation skills before the user approves the design.
  • Ask one clarification question at a time and use visual clarification only when the answer is genuinely easier to see than to read.
  • Explore 2-3 viable approaches, include trade-offs, and state a recommendation before locking the design.
  • Save the approved story spec under docs/superpowers/specs/ and run a self-review for placeholders, contradictions, ambiguity, and scope.
  • After approval, transition only to writing-plans; do not jump directly into execution.
Failure modes to catch
  • The spec lives only in chat and cannot be used by a later agent.
  • The feature contains multiple independent subsystems but is kept as one oversized spec.
  • The team starts coding from assumptions rather than an approved design.
Evidence expected before handoff
approved spec pathapproach trade-off notesuser approval signalopen questions resolved or explicitly deferred

04 · SP-B - Handoff & Workspace Isolation

This card establishes the execution environment. It confirms the approved spec, checks the current workspace, chooses the right isolation mechanism, and records baseline verification before planning.

Why
A clean workspace keeps user changes separate from implementation work and gives final verification a trustworthy before/after comparison.
How
Prefer the harness-native workspace or worktree support. If unavailable, use a git worktree only after checking current status and user preference.
Operating rules
  • Detect existing isolation before creating anything; never nest a worktree inside an existing worktree.
  • Prefer harness-native workspace tools; use git worktree fallback only when no native mechanism exists.
  • Ask for consent before creating a worktree unless project instructions already specify the preference.
  • For project-local worktrees, verify .worktrees/ or worktrees/ is ignored before creating it.
  • Run setup and baseline tests before implementation so later failures can be compared honestly.
Failure modes to catch
  • Manual git worktree conflicts with harness-managed workspace state.
  • A worktree directory appears in git status because ignore verification was skipped.
  • Implementation proceeds on a failing baseline without recording that failures were pre-existing.

04 · SP-C - Write Implementation Plan

The plan decomposes the approved spec into task-sized steps, files likely to change, verification commands, dependencies, and rollback notes.

Why
Subagents perform best with explicit task boundaries and a shared execution ledger. The plan reduces coordination drift.
How
Run writing-plans after spec approval and baseline capture. Keep tasks small enough to review independently.
Operating rules
  • Start from the BMAD story file, approved spec, baseline notes, and BMAD/TEA artifacts rather than chat memory.
  • Map file responsibilities before slicing tasks; each file should have one clear responsibility unless the repo pattern says otherwise.
  • Every task needs exact file paths, interfaces consumed and produced, concrete test code or commands, expected output, and no placeholders.
  • Keep steps bite-sized enough for task-level TDD and review; each task should end with an independently testable deliverable.
  • Self-review for spec coverage, placeholder language, type consistency, and missing requirements before execution handoff.
Failure modes to catch
  • Plan says 'add validation' or 'write tests' without concrete code or commands.
  • Later tasks refer to names, types, or helpers never defined by earlier tasks.
  • A subagent cannot execute its task without hidden context from the planning chat.

04 · SP-D - Subagent-Driven Execution

The controller dispatches task-specific briefs, receives reports, verifies changes, and advances the ledger. Implementers do not need the full session history.

Why
Fresh context keeps implementation focused and reduces accidental coupling between unrelated tasks.
How
Use subagent-driven development where available. After each task, review, verify, and update progress before dispatching the next task.
Operating rules
  • Use a fresh implementer subagent per task and provide only the task brief plus required context.
  • Run a pre-flight plan scan for internal conflicts before dispatching Task 1.
  • Review every task with one reviewer that returns both spec-compliance and code-quality verdicts.
  • Use .superpowers/sdd/ for task briefs, reports, diffs, and the progress ledger; treat it as ignored working-tree scratch.
  • Do not pause between tasks unless blocked, genuinely ambiguous, or complete.
  • Run one broad final review before finishing the branch.
Failure modes to catch
  • Implementer inherits too much session history and optimizes for the wrong context.
  • Controller suppresses review findings or pre-rates severity.
  • Ledger is deleted by git clean -fdx and progress must be reconstructed from commits.

04 · SP-E - TDD Implementation Gate

This card gates production changes behind failing tests, minimal green implementation, refactor, and verification.

Why
TDD reduces accidental behavior changes and makes every task produce executable evidence.
How
Start from ATDD or unit tests, confirm red, implement the smallest viable change, then refactor with tests green.
Operating rules
  • No production code before a failing test or executable acceptance scaffold proves missing behavior.
  • Run red and confirm the failure is meaningful before writing the minimal green implementation.
  • Keep the green change small; avoid bundled refactors while chasing pass state.
  • Refactor only while tests are green and re-run the relevant tests after the refactor.
  • For regressions, prove red-green by showing the test fails without the fix and passes with it.
Failure modes to catch
  • Test passes before code exists and therefore cannot guard the behavior.
  • Production code is written first and tests are retrofitted to the implementation.
  • Refactor changes behavior because the safety net was not re-run.

04 · SP-F - Systematic Debugging

Systematic debugging reproduces the failure, narrows the search space, forms hypotheses, tests them, and records the fix.

Why
Random patching wastes time and often hides the true defect. A structured loop creates durable understanding.
How
Use logs, focused tests, diffs, and binary search. Stop when the root cause and verification evidence are both clear.
Operating rules
  • Do not propose fixes before root cause investigation is complete.
  • Read the full error, reproduce consistently, inspect recent changes, and gather boundary evidence for multi-component systems.
  • Find working examples, compare differences, then test one hypothesis at a time.
  • Fix the root cause, not the symptom, and add a regression test whenever practical.
  • After three failed fixes, stop and question the architecture with the user before attempting another patch.
Failure modes to catch
  • Multiple unrelated changes are bundled, so the actual fix cannot be identified.
  • The symptom disappears locally but the original root cause remains.
  • Reference implementation was skimmed and a subtle pattern requirement was missed.

04 · SP-G - Code Review & Feedback Reception

This card performs focused task review and broader branch review, then routes findings back into implementation or Correct Course.

Why
Review is the quality gate between working code and trusted code.
How
Review diff, tests, architecture fit, error handling, security, and user behavior. Classify feedback by severity and owner.
Operating rules
  • Request review after each SDD task, after major features, and before merge.
  • Reviewers receive a focused work product and SHAs, not the full controller session history.
  • Critical issues must be fixed immediately; Important issues must be fixed before proceeding.
  • When receiving feedback, read it completely, verify against codebase reality, then implement or push back with technical reasoning.
  • Clarify unclear multi-item feedback before implementing a partial subset.
Failure modes to catch
  • Review happens only at the end, after defects have compounded across tasks.
  • Feedback is accepted performatively without checking whether it is technically correct for this codebase.
  • Minor suggestions become scope creep because YAGNI was not checked.

04 · SP-H - Verification Before Completion

This card compares final state against baseline, plan, spec, ATDD, automation, and review findings.

Why
A branch is complete only when behavior and evidence both match the contract.
How
Run targeted and broad checks, inspect remaining diffs, confirm review closure, and document any known limitations.
Operating rules
  • No completion, pass, fixed, or ready claim without fresh verification evidence.
  • Identify the exact command or checklist that proves each claim, run it fully, read output, and check exit code.
  • Compare final state against baseline so pre-existing failures are not blamed on the current branch.
  • Verify requirements line by line; passing tests alone do not prove every requirement is met.
  • Inspect final diff for unrelated churn, debug code, secrets, and unreviewed generated artifacts.
Failure modes to catch
  • The summary says done because an agent reported success, not because the controller verified output.
  • A partial test is extrapolated into a full quality claim.
  • Known failing baseline is not separated from new regressions.
Evidence expected before handoff

04 · SP-I - Finish Development Branch

This card packages final evidence, cleans the branch, prepares a PR summary, and asks for user approval before publishing or merging.

Why
Finishing is where implementation becomes a durable artifact for the team.
How
Use finish-branch discipline: clean status, coherent commits, verification evidence, PR notes, and explicit user direction.
Operating rules
  • Verify tests before presenting finish options.
  • Detect whether the branch is a normal repo, named worktree, or detached/head harness-managed workspace.
  • Present the structured options: merge locally, push PR, keep branch, or discard; detached HEAD removes local merge.
  • Do not clean up a worktree for PR or keep-as-is flows.
  • Clean up only worktrees that the workflow owns, and require exact typed confirmation before discard.
Failure modes to catch
  • Branch is merged or PR is opened before final tests are checked.
  • Harness-owned workspace is deleted and the tool loses track of state.
  • Discard path deletes work without explicit confirmation and commit summary.
Evidence expected before handoff
test verificationworkspace statebase branchchosen finish optionPR or merge summarycleanup result

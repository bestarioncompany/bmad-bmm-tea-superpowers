SPP Core Principles

These principles apply to every SPP card. They are the enterprise guardrails that keep Superpowers from becoming another loose checklist.

1. Skill routing is mandatory
  • If a Superpowers skill may apply, route to it before acting.
  • Do not rationalize with too simple, already know this, or just this once.
  • Use direct skill names when combining with BMAD or TEA so one driver owns the step.
2. Design precedes code
  • Creative implementation starts with story/context review, one-question clarification, 2-3 approach comparison, and explicit approval.
  • The approved spec is written to a durable file before planning.
  • No scaffolding, production code, or implementation skill runs before design approval.
3. Plans are execution contracts
  • Implementation plans contain exact files, interfaces, commands, expected outputs, and no placeholders.
  • Tasks are independently testable slices, not broad todo items.
  • SPP plans encode RED-GREEN-REFACTOR steps so downstream workers do not improvise test strategy.
4. TDD is an iron law
  • No production behavior without a failing test observed first.
  • If implementation code was written before the failing test, delete it and restart from the test.
  • GREEN means minimal code only; refactor happens after tests pass and stays behavior-neutral.
5. Debug root cause first
  • No fixes before reproducing, reading errors, checking recent changes, tracing data flow, and forming a testable hypothesis.
  • One hypothesis, one minimal change, one verification loop.
  • After repeated failed fixes, stop and question the architecture rather than stacking patches.
6. Review early, receive skeptically
  • Each task is reviewed for spec compliance and code quality before the next task compounds mistakes.
  • Critical and Important findings block progress until fixed or technically escalated.
  • External review feedback is evaluated against the codebase before implementation; push back with evidence when it is wrong.
7. Evidence beats claims
  • No completion claim without fresh command output and exit-code evidence from this run.
  • Previous runs, agent reports, visual inspection, or partial checks are not enough.
  • Final status must reconcile tests, requirements, baseline comparison, review closure, and remaining diff.
8. Artifacts survive memory
  • Specs, plans, task briefs, reports, review packages, ledgers, and verification summaries carry state across sessions.
  • Scratch execution evidence belongs in self-ignored SPP space such as .superpowers/sdd/ when used.
  • BMAD story/status and TEA evidence artifacts remain the governance layer around SPP execution.
BMAD + TEA integration rule

BMAD owns product context, story status, and sprint governance. TEA owns test architecture and release evidence. SPP owns engineering execution discipline for the selected story. Do not let two methodologies drive the same step at the same time.

Activation & Modes

Use this section as the start/stop boundary. If a required condition is false, route to the owning BMAD, TEA, or SPP artifact instead of guessing.

Use when
  • A BMAD story file exists and the story needs design approval before implementation.
  • The story has product, UX, data, API, security, or edge-case uncertainty.
  • The team needs an approved design artifact before writing an implementation plan.
Do not use when
  • The only work is purely mechanical and already covered by an approved implementation plan.
  • The user is asking for investigation/debugging rather than new behavior.
  • The feature spans multiple independent subsystems that should be split into separate specs first.
Before you run
  • Confirm Create Story has produced {story_key}.md and sprint-status marks it ready-for-dev.
  • Find any supporting PRD, UX, architecture, project-context, parent epic, or TEA Test Design inputs referenced by the story.
  • Check the current repo shape enough to avoid proposing designs that conflict with existing patterns.
  • Know where specs should be saved; default is docs/superpowers/specs/.

Workflow Steps (6 Steps)

Use the brainstorming skill with one question at a time, capture constraints and trade-offs, then save the approved spec under docs/superpowers/specs/.

01

Read story and context

Action

Treat {story_key}.md as the canonical input; use PRD, architecture, parent epic, and repo patterns only as context.

Why it matters

Prevents chat memory or stale assumptions from becoming requirements.

How to do it

List the exact source files and mark any missing decisions before asking questions.

storycontext
02

Clarify one question at a time

Action

Ask focused questions about users, flows, constraints, data, edge cases, and success criteria.

Why it matters

Small questions are easier to answer and make ambiguity visible early.

How to do it

Prefer short options when helpful; pause on material uncertainty.

clarify
03

Compare 2-3 approaches

Action

Present viable design options with trade-offs, risks, and a recommendation.

Why it matters

Superpowers expects exploration before locking in a design.

How to do it

Compare impact on implementation, tests, maintainability, and user behavior.

optionstrade-off
04

Write the spec

Action

Capture final behavior, interfaces, constraints, open questions, and test strategy.

Why it matters

The implementation plan must read from a stable artifact, not a conversation fragment.

How to do it

Save a clear spec with scope, non-goals, acceptance signals, and verification notes.

spec
05

Self-review the spec

Action

Check the spec for ambiguity, missing edge cases, and mismatches with BMAD context.

Why it matters

A weak spec creates rework in every downstream card.

How to do it

Review against story acceptance criteria, architecture boundaries, and likely failure paths.

quality gate
06

Get user approval

Action

Ask the user to approve or revise the spec before planning begins.

Why it matters

This is the formal handoff from design discovery into execution.

How to do it

Only continue when the spec is explicitly accepted or revised into an accepted state.

approval

Rules and Evidence

Operating rules
  • Do not write implementation code, scaffold files, or invoke implementation skills before the user approves the design.
  • Ask one clarification question at a time and use visual clarification only when the answer is genuinely easier to see than to read.
  • Explore 2-3 viable approaches, include trade-offs, and state a recommendation before locking the design.
  • Save the approved spec under docs/superpowers/specs/ and run a self-review for placeholders, contradictions, ambiguity, and scope.
  • After approval, transition only to writing-plans; do not jump directly into execution.
Failure modes to catch
  • The spec lives only in chat and cannot be used by a later agent.
  • The feature contains multiple independent subsystems but is kept as one oversized spec.
  • The team starts coding from assumptions rather than an approved design.

Applied Example

Scenario

A story asks for passwordless login, but the repo already has email/password auth and the risk model is not locked.

Correct use

Read auth architecture, clarify magic link vs OTP, compare token-table vs signed-link approaches, then write the approved spec with expiry, replay, rate-limit, email failure, and test signals.

Common failure

Start coding an OTP endpoint because it sounds simple, then discover product expected magic links and architecture forbids a new token store.

Troubleshooting

Signals that this card is going wrong
  • The spec lives only in chat and cannot be used by a later agent.
  • The feature contains multiple independent subsystems but is kept as one oversized spec.
  • The team starts coding from assumptions rather than an approved design.
Recovery moves
  • If a required input is missing, route to the previous BMAD, SPP, or TEA artifact instead of filling the gap from memory.
  • If evidence is stale or second-hand, rerun the smallest command or checklist that proves the claim.
  • If scope expands during execution, split the work and update the spec or plan before continuing.
  • If review or verification contradicts the plan, fix the artifact trail first so the next worker sees the same truth.
  • Use the terminal state as the exit test: Approved written spec, then transition to superpowers:writing-plans only.
